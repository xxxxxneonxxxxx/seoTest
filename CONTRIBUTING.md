# Правила участия в проекте

## Ветки

`main` содержит проверенную версию проекта. Вносите изменения через Pull Request
из короткой рабочей ветки: одна задача — одна ветка.

Используйте следующие префиксы:

- `feat/...` — новая функциональность, например `feat/request-logging`.
- `fix/...` — исправление ошибки, например `fix/health-response`.
- `chore/...` — документация, настройки и обслуживание, например `chore/repository-config`.

Создавайте новые ветки от актуальной `main`:

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/request-logging
```

Перед переключением веток сохраните текущую работу коммитом или через `git stash`.
Не отправляйте коммиты напрямую в `main`, не удаляйте её и не используйте force push
для этой ветки.

## Коммиты

Один коммит должен содержать одно законченное изменение. В сообщении кратко
опишите, что изменилось; при необходимости поясните причину в теле коммита.

Формат сообщения: `тип: описание`. Используйте типы `feat`, `fix` и `chore`
с тем же смыслом, что и префиксы веток. Например:

```text
fix: исправить ответ для неизвестного маршрута
chore: описать правила работы с репозиторием
```

Перед коммитом проверьте `git status` и diff подготовленных изменений:
`git diff --cached`. Не добавляйте зависимости `node_modules/`, журналы, `.env`
и настоящие секреты. Изменения зависимостей сохраняйте вместе с `package-lock.json`.

## Проверки

Из корня проекта установите зависимости и запустите тесты:

```bash
npm ci
npm test
```

При изменении поведения сервиса обновите соответствующие тесты. Для ручной
проверки запустите `npm start` и проверьте затронутые маршруты. Инструкция запуска
и требования к окружению находятся в [README.md](README.md).

## Pull Request и слияние

- Создайте PR из рабочей ветки в `main`.
- Укажите, что изменилось и зачем; добавьте ссылку на задачу, если она есть.
- Перечислите выполненные проверки и их результаты. Если проверка не выполнена
  или завершилась ошибкой, явно укажите это.
- Перед слиянием устраните замечания ревью и конфликты, добейтесь успешного
  выполнения тестов и всех обязательных проверок CI.
- Используйте **Squash and merge**: заголовок итогового коммита должен кратко
  описывать завершённое изменение.
- После слияния удалите рабочую ветку и обновите локальную `main`.

Эти правила описывают порядок работы. Защита `main` и обязательные проверки
должны быть отдельно настроены в GitHub.
